# Propertyの定義
- ある処理で想定されるすべての入力について、常に同じである性質
- 例
    - sort処理
        - 入出力の配列の長さは同じ
        - （昇順の場合）隣り合う2要素xi, xjについて、常に xi <= xjが成り立つ
        - 要素の増減がない
    - 配列の最後の値を取得する処理
        - 出力は配列の最大インデックスの値と等しい
    - 配列内の最大値を取得する処理
        - 出力は配列内の最大の値と等しい

# 問題点
- Property記述に用いる処理をどこまで信用するか
    - 信用 = 常に意図した処理を行なっているのかの検証を行わないこと
- 実際の要件をpropertyに落とし込むのは難しい
    - 事例テスト + Property Based Testの組み合わせが良い
        - 要件を明示的に確認しつつ、PBTによって入出力の想定もれを防ぐ

# 効果的なPBTの定義
- generatorはなるべくテスト対象の入出力の型にそのまま合わせる
    - 定義上受け入れられる入力をすべて網羅する

# 主要なPropertyの定義の手法
- モデル
    - 入出力の処理をより簡単な処理（挙動が常に正しいと考えられる実装）で書く
- 事例テストの一般化
    - 通常の単体テストからPropertyを考える
- 不変条件
    - 入出力の前後で常に真となる性質
    - 一つだけでは不足するが、複数組み合わせることで品質の底上げが図れる
        - 要件を表す複雑なPropertyではなく、分解した単純なPropertyを用いる方が良い
            - PBTにより入力値全体に対する理解を深められるチャンスが得られるため
- 対称プロパティ
    - 順方向の処理と逆方向の処理がある場合に用いる
    - 元の入力と逆方向(順方向(入力))が一致するか
